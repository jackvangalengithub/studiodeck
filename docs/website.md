# StudioDeck Website — version 1

Studio admins open **Website** in the workspace. The `/website` overview has a single **Edit website** button beside **Publish website**; its saved preview is not interactive. Edit website opens the dedicated editor at `?edit=1`, with a 70/30 website-and-chat layout and a compact **Back to studio** button. The desktop/mobile switch and **Add your projects & testimonials** button stay in the top bar. The content popup has **Projects** and **Testimonials** tabs, each with its connected content, edit controls and an add button. The editor uses the main app’s warm-grey color variables and contains only content tools; publishing, domains, export and version restoration live in the overview’s **Publish website** popup, with **Publish**, **Domain** and **Published versions** tabs. Payment controls are managed elsewhere in the app. Reset stays on the overview; **Add your projects & testimonials** is in the editor. **Code** smoothly changes the split to 50/50; **Add project** opens a picker and public-copy review. On small screens the preview and tools stack, with independent scrolling. Build and preview freely; publishing and ZIP export require the **€39/month** Website add-on, purchased with a studio package or through the standalone Website checkout. No Stripe products, live payments, domains or external hosting are configured merely by deploying this code.

## Editor and publishing

New websites open on a welcome screen with a gallery of **26 starting points**: the ten original designs, fifteen expressive designs (three for each business type), and **Blank page** as the last card. The business filter starts with the studio’s known business type; **All businesses** exposes the full catalog. Style filters include Modern, Classic, Minimal, Editorial, Organic and Experimental. Blank page remains last under every filter. The new collections explore collage, graphic poster and circular layouts with palettes and example imagery suited to each discipline. Each has a full-screen example; example content is clearly identified and is not copied as real client work. Choosing a different design later explicitly replaces the draft and can be undone.

The saved `index.html`, `styles.css` and `script.js` are the authoritative website source. Templates only seed these files. Chat can change the entire design, text, layout and vanilla JavaScript interactions. The Code panel uses a locally bundled CodeMirror editor with HTML/CSS/JavaScript syntax highlighting, line numbers, bracket matching, indentation, completion, undo, search/replace and Ctrl/⌘ S to save. Prettier formats each fresh file when opened, with two-space indentation and conservative HTML whitespace handling. **Format code** or Shift+Alt+F reformats subsequent edits; formatting is a single undoable edit and incomplete syntax is left untouched. Formatting stays in the draft until saved and published. File tabs, copying and importing support work created with another LLM. Switching between Chat and Code preserves unsaved files and the loaded preview; Back to studio saves pending source edits. No framework, build tool or additional pages are required. Existing structured drafts receive an initial source version; their published files remain untouched until explicit republishing.

Chat receives the current files, recent conversation, reviewed public materials and accessible project names. A request such as “add the Miller family project” first opens the public-copy review, then continues the design edit after the user selects text/images. Private project descriptions and unselected images are not automatically supplied to the model. Exact source patches are applied atomically; failed or ambiguous edits leave the draft unchanged. Fifty successful AI edits per UTC calendar month are allowed per studio, with a ten-request hourly limit; failed edits and project-selection requests release their monthly allowance. Direct source editing works without AI.

Use **Add your projects & testimonials → Projects → Add project** in the editor, or **Prepare website copy** in project settings, to review the public title, description and selected images. No images are preselected. Inspect image descriptions before publishing; filename/title suggestions are not verified visual descriptions. Public location is blank until explicitly supplied. Website projects have their own stable IDs, page anchors, images, visibility and optional category/location. Update from project explicitly replaces the title, description and selected gallery; it preserves the page anchor and inclusion setting. A removed source project leaves the website copy intact. Hiding a project affects the next publish only.

Testimonials belong to their original StudioDeck project. Open **Project settings → Manage testimonials**, or **Add your projects & testimonials → Projects → Project testimonials** in the editor. The content popup’s **Testimonials → Add testimonial** button creates an independent website quote, optionally linked to a website project, with photo, video and publication permission fields. Project team members with active project access can edit name, role/title, quote, photo, YouTube link and publication permission; read access follows the project’s normal access rules. Edits use revision checks. Only approved testimonials can be selected in the website project-import popup; new imports leave them unselected for review.

Import creates independent website copies, linked to the public project copy and original testimonial ID. Updating or removing an original never changes a website draft or published site automatically. Explicitly update the website project to refresh selected testimonials, then publish. Hiding a public project hides its linked quotes in the next draft. Website reset preserves all original project testimonials and photos. Deleting the source project cleans up originals while existing website snapshots remain independent. Earlier studio-wide website testimonials are retained as legacy copies and can be assigned to a public project in the website editor.

Quotes can appear alongside their project or elsewhere on the one-page design. Material controls update marked project/testimonial blocks while preserving unrelated source; if manually authored content no longer has its material markers, use chat or Code to adjust that content. Video links open YouTube; uploaded video hosting is not included. Contact is an email link, not a server-side lead form.

**Save draft** updates the private, authenticated, noindex preview. JavaScript interactions run in an opaque-origin sandbox. Before the publish confirmation, browser checks load the saved page at desktop/mobile widths and report startup errors, missing eager images and horizontal overflow. Server checks reject unsupported files, foreign assets and broken internal anchors; these checks do not guarantee every possible interaction is correct, so review the preview. **Publish website / Publish changes → Publish now** in the publishing popup builds a version before switching the current pointer atomically. Existing project changes, archive/expiry/deletion and draft edits never rewrite published files. A failed or stale build leaves the previous version active. **Undo** retains the last 30 draft saves. **Restore to draft** loads a published version without changing the live website; review and publish to restore it publicly. Revision checks reject stale writes across tabs.

**Start from scratch** on the Website overview asks for confirmation, takes the published website offline, and permanently clears the draft, conversation, website-only images/materials, undo history and published versions. It returns to the welcome screen. Original StudioDeck projects, domain setup, subscription and AI allowance are retained. Reset does not cancel billing. Stale reset requests are rejected.

Publication generates one `index.html`, `styles.css`, `script.js`, responsive JPEG/WebP images at up to 480/960/1600 pixels, metadata-free compressed outputs, width/height attributes, lazy loading, prioritized cover image, canonical URLs, page titles/descriptions, Open Graph tags, Organization JSON-LD, sitemap, robots.txt and a 404 page. Legacy project-page URLs generate redirects to the corresponding one-page anchors. `_redirects` and HTML fallback redirects are included for compatible static hosts. Stable `assets/{id}.jpg` and `.webp` aliases support images referenced by CSS or JavaScript. Image originals are retained independently of source projects. JPEG camera orientation is normalized when PHP EXIF is installed. PHP GD JPEG/WebP support is required; AVIF is not generated in v1.

Limits: 160 KB HTML, 100 KB CSS, 80 KB JavaScript; 50 website projects, 20 images per project, 50 testimonials, 20 MB / 24 megapixels per uploaded image, 500 MB total original image data per studio, 10 publishes/hour. Published versions and image originals currently remain retained; include them in storage monitoring and backups. No automatic cleanup deletes published versions. Export contains **public files only**, no private draft metadata, credentials or application dependencies. Relative page/image links make the bundle portable. Canonical metadata and sitemap target the publishing origin; republish with the correct domain before exporting for that domain, or adjust them when moving to another origin.


Generated JavaScript never runs with the workspace’s origin privileges. Private previews inline their approved image assets and use `sandbox="allow-scripts allow-popups"` without `allow-same-origin`; hosted public HTML enforces the same sandbox through its CSP response header. Network requests, frames, workers, external dependencies and form submissions are disabled. Contact and video links open external destinations. ZIP exports include `_headers` for compatible hosts. When moving an export to another host, preserve this CSP or use a dedicated origin with no application cookies or private routes; a meta tag cannot enforce the CSP sandbox directive. See [MDN’s sandbox header reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/sandbox).

## Application deployment

The schema is created by the normal bootstrap. Public requests to `/sites/{studioId}/` read the active snapshot from `WEBSITE_STORAGE_PATH` (default `storage/websites`), not the database. Keep this entire storage directory outside the web root: it also holds private drafts and release manifests. The router only serves an allowlist of generated public filenames. The app's normal authenticated asset gateway remains unchanged.

Persist and back up both the database (original images/draft/history/billing) and website storage (published versions). PHP needs permission to write the website directory. All web nodes and the billing worker must share that directory and database. The worker updates the public paid-through manifest on renewal/cancellation. Public requests stop serving expired subscriptions without querying the database. A project plan expiry does not affect the separately paid website. Website cancellation retains paid access through its current period; an ended subscription stops serving the site and preserves drafts/files for later recovery.

Set `STRIPE_PRICE_WEBSITE` using `php scripts/setup-website-stripe.php` with a test key first; use `--live` only during an intentional production setup. The script creates a separate EUR recurring product; it does not alter EUR project prices. The configured price is validated as €39 EUR monthly during checkout. Existing USD price IDs must be replaced with the EUR price ID returned by the setup script; existing subscriptions are not migrated automatically. The existing verified webhook events, durable event inbox, billing worker, customer and portal are reused. The portal must permit subscription cancellation and continue disallowing plan switching. Website does not consume seats/project slots. Package purchases include Website on the studio subscription; existing standalone Website subscriptions continue to work and are protected against duplicate billing. Paid invoice verification unlocks publication; checkout redirects alone do not.

`WEBSITE_LOCAL_FREE=true` enables publication **only when APP_ENV=local**. The local Docker Compose override defaults this flag to true; set `WEBSITE_LOCAL_FREE=false` explicitly to test the paid publishing gate. It is for local development, not a production entitlement. Keep it false in production. No paid AI or Stripe calls are made by the tests.

## Domains and HTTPS

The included path address works as soon as the main application is hosted. V1 provides manual custom-domain onboarding; automatic registrar sign-in/Domain Connect and embedded domain purchases are deferred.

For custom domains, first configure a hosting gateway that forwards the customer's **original Host** to this application's router and provisions HTTPS only for verified domains. Set `WEBSITE_CNAME_TARGET` to a hostname pointing to that gateway. The UI asks the user for a www/subdomain, supplies a CNAME and a random TXT ownership token at `_studiodeck.{hostname}`, then verifies both through DNS. The domain remains pending until verification succeeds. Changing a domain creates a new token. Hostname ownership is reserved across studios. Do not change customer MX/TXT mail records or transfer nameservers.

After verification, **publish** to switch canonical URLs and the public domain. The included `/sites/{studioId}/` address redirects to the custom domain. The router rejects unrecognized hosts; it does not expose authenticated app routes on customer hosts. Bare/apex domains are not supported by this CNAME-only flow: redirect the apex to www at the customer's registrar/hosting provider. DNS propagation is asynchronous and may require checking again.

A gateway can use `GET https://APP_HOST/website-tls-check?domain=www.customer.example` as an on-demand certificate authorization endpoint (200 for verified hostname, 403 otherwise). Configure the gateway's normal ACME issuer and rate controls; this PHP endpoint only authorizes issuance and does not itself provision TLS. For example, in Caddy's global `on_demand_tls` block use an `ask` URL pointing at that endpoint, then enable `tls { on_demand }` on the dedicated customer-domain proxy listener. Adapt to your existing proxy configuration rather than replacing the application's server configuration. Keep certificate data persistent. Test a real domain and certificate end to end before enabling custom-domain marketing in production.

Production activation therefore requires: a verified Stripe price/webhook, the running worker, persistent website storage, and (for custom domains) the TLS gateway and CNAME target. The Domain tab reports missing hosting configuration; subscription requirements are enforced by the publishing and export APIs.

## Verification

- `php tests/test_website.php` exercises all 26 source templates, mocked AI edits/project lookup, atomic patches, preserved custom code, source deletion, independent snapshots, stale writes, failed builds, image output, cross-studio assets and subscription isolation.
- `php tests/test_project_testimonials.php` checks project ownership, permissions, source/copy isolation, photo retention, project visibility and deletion.
- `php tests/test_website_stripe.php` verifies dedicated checkout, idempotency, paid invoice enforcement and studio-subscription isolation with a mocked transport.
- `python3 tests/test_website_api.py` runs an isolated HTTP server/database and checks admin/CSRF isolation, previews, publish/export, undo/restore, and unavailable provider handling. Needs PHP SQLite/GD/ZIP and Python Pillow.
- `tests/test_website_formatting.mjs` checks initial formatting, HTML/CSS/JavaScript formatting, keyboard shortcuts, single-step undo/redo, invalid syntax, preview continuity and protection against stale formatter results, using the same isolated browser fixture.
- `tests/test_website_browser.mjs` uses `WEBSITE_FIXTURE`, `PLAYWRIGHT_MODULE`, `CHROMIUM_EXECUTABLE` and `STUDIODECK_TEST_URL`. Export a fixture with `STUDIODECK_TEST_EXPORT=/tmp/website-fixture python3 tests/test_website_api.py`, then serve the app with the matching database/storage environment. It checks gallery entry, the editor’s 70/30 and 50/50 modes, CodeMirror editing, preview continuity, editor deep links, project-testimonial import/management, publishing, reset and mobile layouts. AI tests use a mocked model response, not a paid live provider.


## Building the optional code editor bundle

The app serves `public/assets/vendor/website-editor.js` and the lazy-loaded `website-formatter.js` locally and loads it only when Code is opened. The customer’s exported website has no CodeMirror dependency. To rebuild, run `npm ci` and `npm run build` in `scripts/website-editor/`; commit the generated bundle along with any dependency-lock changes. Third-party notices are included beside the bundle. The normal PHP deployment needs no Node build step.

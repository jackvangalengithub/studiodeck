# Video slides and photo motion

In **Add slide → Video**, upload an MP4 or WebM (up to 100 MB), or enter a YouTube link. Choose **Standard** or **Full screen**, and **Fit entire video** or **Crop to fill**. Enable **Play automatically when this slide appears** for muted autoplay. Standard-layout videos have native controls for sound and replay. Full-screen uploaded videos hide the native controls for clean presentation playback; a Play button is available before playback when needed. Uploaded videos play once and hold their last frame; YouTube retains its own player and end screen. Full screen fills the slide area; the presentation's existing fullscreen control expands the whole presentation.

For a photo, render, full-photo slide or other image, open **Edit slide → Add motion**, or use **Add motion** beneath the image. Gentle left-to-right, right-to-left and pull-back movements need no AI connection. Choose 4, 6, 8, 10 or 12 seconds, preview, then apply. Movement plays once on slide entry and eases back to the actual image. Navigating back starts it again; routine background refreshes preserve playback progress. In scroll mode only the active slide plays.

**AI camera movement** generates an eight-second clip before presenting. Choose a left-to-right, right-to-left, pull-back or gentle-orbit preset, or start with Custom. Presets only fill the editable instructions textarea; generation uses the text you write. Generate a preview, then reopen **Add motion** when the ready notification appears. The instructions are saved with the clip. Preview the clip before applying it. Editing its instructions requires generating and reviewing a new preview. Generating another clip does not replace the currently applied movement. Playback blends into the selected photo at the end, so the final image is always the real stored photo. New viewpoints may interpret unseen details; review before sharing.

## Server configuration

Create a key in [Google AI Studio](https://aistudio.google.com/app/apikey) and [enable paid API billing](https://ai.google.dev/gemini-api/docs/billing) for its Google Cloud project. Veo requires a paid API tier. Set these in the server `.env`:

```dotenv
GEMINI_API_KEY=your-google-api-key
GEMINI_VIDEO_MODEL=veo-3.1-fast-generate-preview
VEO_PROJECT_LIMIT=10
```

For Docker Compose, reload the environment for both services, then refresh the app:

```sh
docker compose up -d --no-deps --force-recreate web worker
```

For other deployments, restart both the web and worker processes with the updated environment. Google bills video generation separately. `VEO_PROJECT_LIMIT` caps explicit generation attempts per project, including failed attempts, to avoid assuming interrupted requests were free. No video request is made during presentation playback. The key remains on the server. Existing gentle motion and uploaded videos work without it.

The worker submits one request, persists its operation identifier, then polls in subsequent worker ticks. It can process other jobs while Google generates. A failed request is never blindly resubmitted through **Retry file**; generate another preview explicitly. Provider calls time out, pending operations expire after 30 minutes, and results are rejected if the source image or iteration changed.

Your instructions are sent to Veo with a fixed eight-second duration and a final-photo ending instruction. The first constraint image is a gentle centered crop of the selected image; the last contains the entire selected image. Both use the same 16:9 or 9:16 canvas. Generation uses Veo's [first/last-frame support](https://ai.google.dev/gemini-api/docs/veo). REST image serialization follows Google's [official SDK converter](https://github.com/googleapis/python-genai/blob/main/google/genai/models.py) (`bytesBase64Encoded` and `mimeType` for `predictLongRunning`). Generated bytes are downloaded into project storage, rather than depending on temporary Google URLs.

## Playback and storage

- Reduced-motion preferences suppress automatic video/photo motion. A user can still explicitly play a video or preview a movement.
- Video autoplay is muted and inline. A Play button remains available if a browser blocks it. A failed photo clip leaves the real image visible.
- Navigation stops playback; slide-transition copies cannot create duplicate players. Hidden tabs pause playback.
- Current/next video blobs are fetched with the same authentication headers as images and cached with a small size-limited entry count. Large uploaded clips must finish downloading before initial playback; preloading the next slide helps. Use compact clips for prompt starts.
- Media is stored in `slide_media`, belongs to a project, counts toward trial storage, and is deleted with its project. Serving verifies iteration access and the slide's media reference, including HTTP byte-range support.
- AI preview candidates and saved generation instructions are visible only to designers. Clients can fetch only applied clips belonging to their iteration. Image changes invalidate old motion; copied iterations retain the same immutable media until edited.

## Verification

`tests/test_slide_media.py` uses temporary databases and injected provider responses. It checks uploads, ranges, access controls, source changes, review/apply, locked iterations, shared snapshots and project deletion. `tests/test_slide_media_browser.cjs` uses intercepted local fixtures to check editor controls, preview/apply, autoplay, final still photos, mobile layout and reduced motion. Neither test makes paid API calls.

Generate the two-second local fixture with `node tests/create_media_fixture.cjs`, setting `MEDIA_TEST_VIDEO` to the desired output path. Export the backend fixture with `MEDIA_BROWSER_EXPORT`, then pass the same paths to the browser test, along with `PLAYWRIGHT_MODULE` and `CHROMIUM_EXECUTABLE` when needed. The PHP test needs the dependencies in the project Docker image.
